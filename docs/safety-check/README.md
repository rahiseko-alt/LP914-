# 安全確認 — 固定表と運用手順

用語は `../../CONTEXT.md` に従う。なぜこの形にしたかは `../adr/0001`〜`0004` にある。

## これは何か

アプリが安全かどうかを、**何回やっても同じ結果になる形**で判定するための一式。
検査の道具ではない。**終わりを決めるための表**である。

- `asvs-5.0.0-l1.csv` — OWASP ASVS 5.0.0 の L1 **70項目**（公式データをそのまま同梱）
- `table/` — 固定表。章ごとに1ファイル。各項目に合格基準が事前に書いてある
- `results/<対象アプリ>/` — 判定結果
- `../../scripts/check-table.py` — 固定表の検品（表そのものに穴が無いかだけを見る）

## 回しかた

1. **表を当てる。** `table/` の各項目を、上から順に対象アプリへ当てる。
   判定に使ってよいのは次の3つだけで、これ以外を根拠にしない。
   - 機械の出力（表に書かれた命令を実行した結果）
   - コード本体
   - 経緯の記録（対象アプリの中にある、設計の意図と決定を書いた文書）
2. **判定を出す。** 合格・不合格・判定不能の三段階。各項目に根拠のファイル名と行番号を付ける。
   - どの情報源にも根拠が無ければ**判定不能**。合格に倒さない
   - 経緯の記録とコードが食い違ったら、**コードを正**として不合格
   - 該当機能が無い項目は「合格（該当機能なし）」として数え、集計で内訳を分ける
3. **検品する。** `python3 scripts/check-table.py` を実行する。終了コードが 0 でなければ、
   その先の判定は信用しない。
4. **終わりを確かめる。** 判定結果の行数が固定表の行数と一致していれば、確認は終わっている。
   多ければ、途中で項目が増えている。
5. **判定不能を潰す。** 1件でも残っていれば `grilling`（掘り下げヒアリング）を起動する。
   - **技術を聞かない。業務の事実を聞く。**
     「行単位アクセス制御は適切か」ではなく「このカルテは別の店のスタッフに見えてよいか」
   - 必ず**推奨する答えを先に添える**。「はい」「違う」で答えられる形にする
   - 1問で終わらせない
   - 得た答えは**対象アプリ側の経緯の記録に書き戻す**。次回からその項目は記録で判定できる

判定不能は回すたびに減り、増えない。これが確認が終わりに向かう仕組みである。

## 固定表の書き方

1項目は次の形で書く。見出しと欄の名前は検品プログラムが読むので、崩すと赤になる。

```
### v5.0.0-8.2.1

- **原文**: （ASVS の原文をそのまま）
- **日本語**: （原文の訳）
- **判定のしかた**: 機械 または 読む
- **見る場所**: （`読む` のときだけ。どこを読むかを命令で絞る）
- **合格基準**: （何が満たされていれば合格か）
- **該当しない条件**: （どういう作りなら該当しないか）
- **根拠として出すもの**: （何を証拠として残すか）
```

- `機械` の項目には、**実行する命令を確定**させ、合格とみなす出力条件を書く。
- `読む` の項目には、**見る場所を命令で絞る**。探索範囲を固定しないと結果が揺れる。
  検品プログラムは、`読む` なのに「見る場所」が無い項目を赤にする。
- **命令が何も見つけられなかったときは、合格ではなく判定不能とする。** 対象アプリの
  書きかたが命令と合っていない可能性があるため。黙って合格に倒さない。
- **命令の出力に紛らわしい行が出たときは、その行を読む。** 本番の画面から到達できない
  試験専用の道具だと確かめられた場合に限り、数に入れない。確かめられなければ数に入れる。
  **読まずに除外しない。**確かめた根拠を判定結果に残す。
- 合格基準に「理論上こういうことも起こりうる」は書かない。**現実に起きるかだけ**で書く。
- 命令は `bash` で実行する前提とする。
