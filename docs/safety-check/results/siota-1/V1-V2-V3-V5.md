**判定: 合格**

### v5.0.0-2.3.1 — 決まった順序どおりでない要求を弾いているか

**判定: 合格**

### v5.0.0-3.4.1 — 暗号化された通信を強制する見出しがあるか

**判定: 不合格**

命令の出力に `strict-transport-security` は **0件**だった。

```
$ curl -sS -I -L --max-time 30 https://trimmer-system.kouheikosehira.com
HTTP/2 200
（strict-transport-security の行は無い）
```

この見出しが無いと、**利用者が `http://` で入ってきたとき、暗号化されない通信のまま
やり取りが始まる隙が残る**。公衆の無線などで割り込まれると、そこで通行証が盗まれうる。

**どうすると直るか**: 配信の手前にいる Cloudflare の設定で「HSTS」を有効にし、期間を
1年（31536000秒）以上にする。または Cloudflare Worker が返す応答に
`Strict-Transport-Security: max-age=31536000` を付ける。前者のほうが漏れがない
（Worker を通らない応答にも付くため）。**判断は対象アプリの持ち主に委ねる。**

**関連して記録しておくこと**: この応答には、他の守りの見出し（内容の種類の取り違えを防ぐ
もの、枠内表示を禁じるもの、読み込み元を制限するもの）も付いていない。**ただし ASVS L1 は
それらを求めていない**ため、この安全確認では不合格にしない。事実として記録するにとどめる。

### v5.0.0-3.4.2 — 他の場所からの読み取りを許す見出しの値が安全か

**判定: 合格**

許す相手の値を、**受け取った値をそのまま返してはいない**。決まった形（手元の開発用の
場所）に合うときだけ、その値を返している（`worker/src/index.js:44-54`）。

```
if (/^https?:\/\/(localhost|127\.0\.0\.1)(:\d+)?$/.test(origin)) { ... }
return {};
```

本番では条件に合わないため、**この見出しを一切返さない**。誰にでも許す指定（`*`）も
使っていない。コードにも「本番は同一オリジンで不要」という注釈がある（同 `:43`）。

### v5.0.0-3.5.1 — 大事な操作への要求が、このアプリの画面から出たものか確かめているか

**判定: 合格**

合格基準の1番目を満たす。**`Authorization` の見出しを必須にしている。**

- 大事な操作を扱う経路はすべて `/api/` の下にあり、そこを通るとき必ず
  `resolveAuthContext` が呼ばれる（`worker/src/index.js:333-335`）。
- その中で `Authorization: Bearer` の見出しを読み、無ければ 401 で止める
  （`worker/src/auth-context.js:39-40`）。
- 例外は `/api/config`（同 `:324`）のみで、これは公開してよい設定値を返すだけ。

この見出しは、他の場所に置かれた罠からは勝手に付けられない。したがって、利用者が気づかない
うちに要求を送られる攻撃は成立しない。ブラウザに保存した記録（クッキー）で利用者を見分けて
いないことも、1.3.1 と 3.3.1 で確かめたとおり。

### v5.0.0-3.5.2 — 事前の問い合わせを起こさない形では呼べないか

**判定: 合格**

3.5.1 と同じ根拠。`Authorization` の見出しを必須にしているため、他の場所からの要求は
**必ず事前の問い合わせを起こす**。事前の問い合わせに対しては、本番では許す見出しを
返さない（3.4.2）ので、そこで止まる。単純な送信だけで大事な操作を呼ぶことはできない。

### v5.0.0-5.2.1 — 処理しきれない大きさのファイルを弾いているか

### v5.0.0-5.2.2 — 種類が想定どおりで、中身と一致しているか

**判定: 合格**

合格基準の2点をどちらも満たす。

1. **許す一覧で決まっている**: 保管場所の設定が
   `array['image/jpeg', 'image/png', 'image/webp']`
   （`supabase/migrations/202607160001_supabase_base.sql:730-733`）。ブラウザ側にも同じ
   対応表がある（`backend/js/supabase-storage.js:1-7`）。
2. **中身が名乗っている種類と一致しているかを確かめている**: `validateAssetContent`
   （`backend/js/supabase-storage.js:19-33`）が**先頭12バイト**を読み、JPEG・PNG・WebP
   それぞれの印と照合する。一致しなければ弾く。上げる処理から実際に呼ばれている（同 `:101`）。

**明記しておくこと**: 2 の中身の照合は**ブラウザ側で動く**。サーバ側（保管場所）が見るのは
名乗っている種類だけで、中身は見ない。したがって、ブラウザを通さず直接上げれば、画像でない
ものを画像と名乗って置くことはできる。ただし、置かれたファイルは誰でも開ける場所に無く
（3.2.1）、命令として実行されることも無い（5.3.1）ため、実害には至らない。固定表が
「明記したうえで合格としてよい」と定めているとおり、明記して合格とする。

### v5.0.0-5.3.1 — 上げたファイルが命令として実行されないか

### v5.0.0-5.3.2 — 置き場所を利用者の付けた名前で決めていないか

置き場所を組み立てているのは `buildAssetPath`（`backend/js/supabase-storage.js:33-41`）
