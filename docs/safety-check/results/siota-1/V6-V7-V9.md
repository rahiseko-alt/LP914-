## 掘り下げヒアリングで何が起きたか

この3章の判定は、**掘り下げヒアリングを通したことで大きく動いた**。

**パスワードの8項目（6.2.1〜6.2.8）が、判定不能から合格（該当機能なし）へ。**
ただしその過程で、**決めたことと実際が食い違っていた**ことが分かった。

1. ヒアリングでマスターが「ログインの入り口は Google だけ。他は許さない」と決めた
2. その決定を裏づけるため、ログインの仕組みの側の設定を確認した
3. **Email provider が有効（Enabled）のままだった。** 画面を通さずにメールアドレスと
   パスワードで誰でも登録・ログインできる状態だった
4. マスターが無効（Disabled）に切り替えた。切る前に、このアプリがメールログインも
   メール送信も使っていないことをコードで確認している
5. 経緯を対象アプリの記録に書き戻した（`docs/decisions.md` の `D-20260915-77`）

**開いていたことで起こりえたこと**: カルテは見られない（勝手に登録した利用者はどの店にも
飼い主にも紐づかず、行単位のアクセス制御で一切のデータに到達できない）。起こりえたのは、
見知らぬアカウントが際限なく作られ、確認メールの送信枠を使い切らせることだった。

**この発見は、合格基準の書き方が生んだものである。** パスワードの8項目に
「画面にパスワード欄が無いだけでは該当しないと扱わない。ログインの仕組みの側が
受け付けないことが記録にあって初めて該当しないとする」と**あらかじめ書いておいた**ため、
判定不能が残り、その解消が設定の確認につながった。基準を緩めていれば、
「画面に無いから該当しない」で通り過ぎていた。

**不合格2件（7.2.4 と 7.4.1）**も、同じヒアリングの中で確定した。ログイン状態の扱いを
公式資料で調べることの承認を得て調べた結果、判定不能だったもの（7.2.4）と、基準の欠陥で
合格としていたもの（7.4.1）が、どちらも不合格だと分かった。

### v5.0.0-7.2.2 — その都度作られる引換券を使っているか

**判定: 合格**

利用者の見分けには、ログインのたびに発行される引換券を使っている
（`worker/src/auth-context.js:39` で受け取り、`:44` で確かめる）。

ブラウザに固定の鍵（`SUPABASE_PUBLISHABLE_KEY`）を置いているが、これは**公開してよい鍵**で
あり、利用者の見分けには使っていない。この鍵だけではデータに到達できず、別に引換券が要る
ことは、行単位のアクセス制御の判定がすべて利用者の身元に依存していることから確かめられる
（V8 の判定結果を参照）。設定の見本にも公開用の鍵として記載がある（`.env.example:4`）。

### v5.0.0-7.2.3 — 引換券が安全な乱数で作られているか

**判定: 合格（該当機能なし）**

対象アプリ自身がログイン引換券を作っている箇所は無い。命令の出力は次のとおり。

| 出たもの | 件数 | 用途（読んで確かめた） |
|---|---:|---|
| `gen_random_bytes` | 3ファイル | 招待コードの生成（6.4.1 で判定済み） |
| `randomUUID` | 2件 | 画像ファイルの名前の生成（`backend/js/supabase-storage.js:63, 71`） |
| `Math.random` | **14件** | すべて `scripts/verify-*.mjs`（手元の検証用の道具）の中。本番に配られるコードではない |

**`Math.random` が0件ではない点を明記する。** 予測しやすい乱数が14か所で使われているが、
いずれも手元の検証用であり、ログイン引換券の生成には使われていない。合格基準が問うのは
「ログイン引換券の生成に使っていないか」であり、それは満たす。

ログインを外部の仕組みに任せていることは、`backend/js/supabase-auth.js:62-76` と
`worker/src/auth-context.js:44` から特定できる。

### v5.0.0-7.2.4 — ログインのたびに引換券が入れ替わるか

**判定: 不合格**

対象アプリ自身は引換券を作っていないため、入れ替えの挙動は任せ先が決めている。
掘り下げヒアリングでの承認を得て公式資料を調べた結果、**既定では前のログイン状態が
終わらない**ことが分かった。

> 既定では、1人の利用者が何台の端末でも、いくつでも同時にログイン状態を持てる
>
> — https://supabase.com/docs/guides/auth/sessions

「1人につき1つだけ許す」設定は存在するが、上位の契約が必要で、既定では無効。しかも
切り替わりは次回の更新時なので即座ではない。

ログインし直しても新しいログイン状態が足されるだけで、前のものは並行して生き続ける。
合格基準の「古いものが使えなくなること」を満たさない。

調べた内容は対象アプリの記録に書き戻した（`docs/decisions.md` の `D-20260915-76`）。
次回からこの項目は記録だけで判定できる。

**どうすると直るか**: 上位の契約に切り替えて「1人につき1つだけ」を有効にする。ただし
切り替わりが即座でない点は残る。

### v5.0.0-7.4.1 — ログアウト後に引換券が使えなくなるか

**判定: 不合格**

**この項目は、いったん合格と判定したものを訂正した。** 合格基準が ASVS の原文を写し取れて
おらず、穴を見逃していた（`../../../adr/0005`）。

合格基準の1点目は満たす。ログアウトは既定で全端末に効き、サーバ側のログイン状態の行が
削除される。記録にも明記がある（`docs/ops/proof-of-red.md:2762-2763`）。実装の裏づけも
公式にある（https://github.com/supabase/auth-js/blob/master/src/GoTrueClient.ts）。

**2点目を満たさない。** 発行済みの通行証（中身入りの引換券）は取り消せない。

> 利用者の通行証を、期限が来る前に取り消す方法は無い
>
> — https://github.com/supabase/auth-js/blob/master/src/GoTrueClient.ts

既定の有効期間は1時間（https://supabase.com/docs/guides/auth/sessions）。つまり
**ログアウトしたあとも、最大1時間はその通行証でデータを読める**。ASVS が求める手当て
（無効にしたものの一覧を持つ、利用者ごとの日時より前のものを弾く等）は、このアプリには無い。

**影響の範囲**: 退職・退会の場面では別の守りが効いている。`shop_memberships.active` と
`owners.active` の確認がアクセス制御に入っているため、通行証が生きていてもデータには
到達できない（7.4.2 は合格）。**残る穴は、本人がログアウトした直後の1時間**である。
端末の紛失・共用端末での操作といった場面で意味を持つ。

**どうすると直るか**: 通行証の中の `session_id` が、サーバ側に残っているログイン状態と
一致するかをアクセス制御の条件に足す。公式が案内している方法である
（https://supabase.com/docs/guides/auth/sessions の FAQ「How to ensure an access token
(JWT) cannot be used after a user signs out」）。通行証の有効期間を1時間より短くすると、
危険な時間はその分だけ縮む。

調べた内容と直しかたは、対象アプリの記録に書き戻した（`docs/decisions.md` の
`D-20260915-76`）。

### v5.0.0-7.4.2 — 利用者を無効にしたとき、到達できなくなるか

お店の人・飼い主の両方について、無効化したときに**すべての経路**で到達が止まる。

判定が1本しかないため、経路の抜けが構造的に起きない。

**飼い主**: 判定は4本あり、そのすべてに `owners.active` の確認が入っている
（`supabase/migrations/202607160007_owner_access_control.sql:47`／`:64-65`／`:85-86`／
`:105-110`）。この4本は、かつて**1本だけ抜けていて「退会済みに見えるのに見えている」
状態だった**ことが記録されており、その修正として4本に揃えられた
（同 `:6-12`、`docs/decisions.md:360`）。

**明記しておくこと**: 引換券そのものは失効させていない。無効にした利用者の画面は、見かけ上

## この判定の限界（正直に記録する）

- **本番で動いている設定は見ていない。** 見たのはコードと、手元用の設定ファイルと、経緯の
  記録だけである。判定不能10件のうち8件は、まさにこの限界から出ている。
- `機械` の5項目は何回実行しても同じ結果になる。`読む` の18項目は文章の判断が入るため、
  完全な再現は保証しない。見る場所を命令で絞ることで揺れを抑えている。
- 7.4.2 は、引換券を失効させていないという事実を含んだうえでの合格である。合格基準を
  「到達できないこと」と定めた結果であり、基準を変えれば判定も変わる。
