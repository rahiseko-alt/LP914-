## v5.0.0-8.1.1 — 認可の文書に規則が定められているか

**判定: 合格**

根拠: `docs/ops/scenarios.md:13-21`

役割が「お店の人」「飼い主」の2つに限定され、それぞれが読める対象・書ける対象が表として
一覧できる。お店の人は自店舗の犬・飼い主・カルテを作る／直す／消すことができ、飼い主は
自分の犬の確定したカルテを読むだけ、と書かれている。役割の列挙にとどまらず、対象と操作の
範囲まで書かれているため合格条件を満たす。

「管理者と一般スタッフを区別しない」ことが仕様であると明記されている点も確認した
（`docs/ops/scenarios.md:20-21`）。これは規則の欠落ではなく、意図された設計である。

## v5.0.0-8.2.1 — 機能ごとのアクセスが権限のある利用者だけに制限されているか

**判定: 合格**

命令の出力: **0行**

外部から触れる11のテーブル（`shops` / `profiles` / `shop_memberships` / `owners` /
`owner_users` / `pets` / `reports` / `report_assets` / `invitations` / `audit_logs` /
`import_ledger`）のすべてで、行単位のアクセス制御が有効になっている。有効でないものは
1件も無い。

根拠: `supabase/migrations/202607160001_supabase_base.sql:599-620`

なお、11のテーブルすべてで `force row level security` も指定されている。これはテーブルの
所有者に対しても規則を適用する指定で、合格条件が要求する水準より厳しい。

**この判定が見ていないもの**: 命令が読むのは宣言されたスキーマであり、稼働中の
データベースの実状ではない。実状は Supabase 公式診断の `0013_rls_disabled_in_public` が
見る。稼働中の診断は今回行っていない（対象アプリの管理画面への接続が必要なため）。

## v5.0.0-8.2.2 — データごとのアクセスが制限されているか（他人の ID で他人のデータが読めないか）

**判定: 合格**

命令の出力: **0行**

誰でも通る全面許可の規則（`using (true)` / `with check (true)`）は1件も無い。

`public.import_ledger` は行単位のアクセス制御が有効でありながら規則が1つも無いが、これは

いる（`supabase/migrations/202607160005_import_ledger_rpc.sql:3, 31`）。意図された設計と
判断し、合格とした。

## v5.0.0-8.3.1 — 認可が信頼できる層で強制されているか

**判定: 合格**

合格条件の3点すべてを満たす。

1. **認可の判定がサーバ側で行われている**: 認可はデータベースの行単位アクセス制御と、
   `private` スキーマに置かれた判定関数（`is_shop_staff` / `is_owner_user` /
   `can_read_pet` / `can_read_final_report` / `can_read_profile` など）で行われている。
   これらの関数は `anon` と `public` から実行権限が剥奪されている
   （`supabase/migrations/202607160001_supabase_base.sql` の `revoke all on function
   private.*` 群）。
2. **ブラウザに渡している鍵が迂回できる種類でない**: ブラウザ側が使う鍵は
   `SUPABASE_PUBLISHABLE_KEY` のみ（`.env.example:4`）。ブラウザ側 JavaScript を検索した
   ところ `service_role` の出現は `backend/js/supabase-storage.js:224` の1件のみで、
   これは設計上の制約を説明した**注釈**であり、鍵の値ではない。
3. **サーバ側の中継が迂回できる鍵を使っていない**: Cloudflare Worker は
   `SUPABASE_PUBLISHABLE_KEY` のみを使い、利用者の持つトークンをそのまま渡して認可を
   データベースに委ねている（`worker/src/auth-context.js:27-36`）。Worker のソース全体を
   検索しても `service_role` の出現は0件だった。

## この判定の限界（正直に記録する）

- 見たのは**宣言されたスキーマとコード**であり、**稼働中のデータベースの実状ではない**。
  移行ファイルの内容と、実際に本番へ適用されている状態が食い違っている可能性は、この
  判定では否定できない。これを埋めるには Supabase の公式診断を稼働中のプロジェクトに

  完全な再現は保証しない。これは固定表の設計上の限界であり、隠さずに記録する。
