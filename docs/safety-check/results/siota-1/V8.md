### v5.0.0-8.1.1 — 認可の文書に規則が定められているか

**判定: 合格**

根拠: `docs/ops/scenarios.md:13-21`

役割が「お店の人」「飼い主」の2つに限定され、それぞれが読める対象・書ける対象が表として
一覧できる。お店の人は自店舗の犬・飼い主・カルテを作る／直す／消すことができ、飼い主は
自分の犬の確定したカルテを読むだけ、と書かれている。役割の列挙にとどまらず、対象と操作の
範囲まで書かれているため合格基準を満たす。

「管理者と一般スタッフを区別しない」ことが仕様であると明記されている点も確認した
（`docs/ops/scenarios.md:20-21`）。これは規則の欠落ではなく、意図された設計である。

### v5.0.0-8.2.1 — 機能ごとのアクセスが権限のある利用者だけに制限されているか

**判定: 合格**

命令の出力: 前半（外から触れるテーブル）**11件**、後半（行単位のアクセス制御が有効なもの）
**11件**。前半にあって後半に無いものは**0件**。前半が0件ではないので判定不能にも当たらない。

```
--- 外から触れるテーブル ---
public.audit_logs      public.import_ledger   public.invitations
public.owner_users     public.owners          public.pets
public.profiles        public.report_assets   public.reports
public.shop_memberships public.shops
--- 行単位のアクセス制御が有効なもの ---
（同じ11件）
```

根拠: `supabase/migrations/202607160001_supabase_base.sql:599-620`

11のテーブルすべてで `force row level security` も指定されている。これはテーブルの持ち主に
対しても規則を適用する指定で、合格基準が求める水準より厳しい。

**この判定が見ていないもの**: 命令が読むのは**移行ファイルに書かれた設計**であり、いま
動いているデータベースの実状ではない。実状は Supabase 公式の点検機能
（`0013_rls_disabled_in_public`）が見る。今回は行っていない（対象アプリの管理画面への
接続が必要なため）。

### v5.0.0-8.2.2 — データごとのアクセスが制限されているか（他人の ID で他人のデータが読めないか）

**判定: 合格**

命令の出力: 1行目 **14**（読んだ移行ファイルの数）、2行目 **0**（誰でも通る全面許可の
規則の数）。1行目が0ではないので判定不能にも当たらない。改行をまたいで書かれた規則も
1行につないでから数えているため、書きかたによる取りこぼしは無い。

`public.import_ledger` は行単位のアクセス制御が有効でありながら規則が1つも無いが、これは
**全面拒否**を意味し、危険ではない。このテーブルへの読み書きは
`read_import_ledger` / `write_import_ledger` / `count_import_ledger` の3つの関数経由だけに
限られている（`supabase/migrations/202607160005_import_ledger_rpc.sql:3, 31, 71`。後に
`supabase/migrations/202609060012_single_staff_role.sql:284, 312, 352` で置き換え）。
意図された設計と判断し、合格とした。

### v5.0.0-8.3.1 — 認可が信頼できる層で強制されているか

**判定: 合格**

合格基準の3点すべてを満たす。

1. **認可の判定がサーバ側で行われている**: 認可はデータベースの行単位アクセス制御と、
   外から直接呼べない場所に置かれた判定関数（`is_shop_staff` / `is_owner_user` /
   `can_read_pet` / `can_read_final_report` / `can_read_profile` など）で行われている。
   これらの関数は、ログインしていない利用者と一般の利用者の両方から実行権限が剥奪されて
   いる（`supabase/migrations/202607160001_supabase_base.sql:698-706`）。
2. **ブラウザに渡している鍵が迂回できる種類でない**: ブラウザ側が使う鍵は
   `SUPABASE_PUBLISHABLE_KEY`（公開してよい鍵）のみ（`.env.example:4`）。ブラウザ側
   JavaScript を検索したところ、すべての制限を無視できる鍵を指す語の出現は
   `backend/js/supabase-storage.js:224` の1件のみ。その行を読んだところ、削除の順序に
   関する制約を説明した**注釈**であり、鍵の値ではなかった。
3. **サーバ側の中継が迂回できる鍵を使っていない**: ブラウザとデータベースの間に
   Cloudflare Worker があるが、使う鍵は `SUPABASE_PUBLISHABLE_KEY` のみで、利用者の
   ログイン情報をそのまま渡して認可をデータベースに委ねている
   （`worker/src/auth-context.js:27-36`）。Worker のソース全体を検索しても、すべての制限を
   無視できる鍵を指す語の出現は0件だった。

## この判定の限界（正直に記録する）

- 見たのは**移行ファイルに書かれた設計とコード**であり、**いま動いているデータベースの
  実状ではない**。書かれている内容と、実際に本番へ適用されている状態が食い違っている
  可能性は、この判定では否定できない。これを埋めるには Supabase 公式の点検機能を、
  動いている側に当てる必要がある。
- `機械` の2項目は何回実行しても同じ結果になる。`読む` の2項目は文章の判断が入るため、
  完全な再現は保証しない。見る場所を命令で絞ることで揺れを抑えているが、ゼロにはならない。
  これは固定表の設計上の限界であり、隠さずに記録する。
