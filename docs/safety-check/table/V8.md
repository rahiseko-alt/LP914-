# 固定表 — V8 認可（Authorization）

OWASP ASVS 5.0.0 の L1 のうち、章 V8 に属する **4項目**。項目は公式データ
（`../asvs-5.0.0-l1.csv`）と1対1で対応し、追加・削除・統合をしない。

判定のしかたは `機械`（実行する命令が確定しているもの）か `読む`（見る場所が確定している
もの）のどちらか。どちらの命令も、**対象アプリの置き場所の最上位で `bash` で実行する**。

出典: OWASP Application Security Verification Standard 5.0.0 (CC BY-SA 4.0)。
日本語は原文からの訳で、訳の責任はこの置き場所にある（`../../adr/0004` 参照）。

## この章の共通の但し書き

- **命令には3つの種類があり、出力が0件のときの意味が逆になる。** どれに当たるかを各項目の
  「命令の種類」に書く。書いていない命令は使わない。
  - **危険な書き方を探す命令**: 0件なら**合格**。探した書き方をしていない、という意味になる
  - **備えを探す命令**: 0件なら**不合格**。在るべきものが無い、という意味になる
  - **対象の一覧を作る命令**: 0件なら**判定不能**。対象が無いのか、命令が対象アプリの書き方と
    合っていないのかを区別できないため（`../../adr/0002`・`../../adr/0006`）
- **命令の出力に紛らわしい行が出たときは、その行を読む。** 本番の画面から到達できない
  試験専用の道具だと確かめられた場合に限り、その行を数に入れない。確かめられなければ
  数に入れる。**読まずに除外しない。読んだ行はすべて、確かめた結果とともに判定結果に残す。
  出力の一部を無記録で落とさない。**
- **命令は対象アプリの置き場所の最上位で `bash` で実行し、表に書いたとおりに実行する。**
  省略や追加をしない。探す範囲に対象アプリ固有の置き場所の名前を書かない。失敗を
  `2>/dev/null` で隠さない（隠すと、別のアプリに当てたとき黙って0件＝合格になる）。
- 8.2.1 と 8.2.2 の命令は、ブラウザからデータベースへ直接つなぐ作り（Supabase など）を
  前提にしている。その作りでない対象アプリでは、各項目の「該当しない条件」に従う。

### v5.0.0-8.1.1

- **原文**: Verify that authorization documentation defines rules for restricting function-level and data-specific access based on consumer permissions and resource attributes.
- **日本語**: 認可の文書に、利用者の権限と対象の属性にもとづいて、機能ごとのアクセスとデータごとのアクセスを制限する規則が定められていること。
- **判定のしかた**: 読む
- **見る場所**: 対象アプリの経緯の記録すべて。次の命令で候補を絞り、挙がったファイルを読む。候補が0件なら、経緯の記録の置き場所（`docs/` に相当するもの）の全ファイルを読む。

  ```
  grep -rlniE '権限|ロール|認可|だれが|誰が|見える|アクセスできる' docs/ *.md 2>/dev/null
  ```

- **合格基準**: 上で挙がった文書のどれか1つの中に、**役割の一覧**と、**役割ごとに読める対象・書ける対象**を一覧できる箇所があること。役割が列挙されているだけ、または個別の決定の記録に断片的に散っているだけでは不合格とする。
- **該当しない条件**: 無い。認可を持たないアプリ（全員が同じものを見る）であれば、その旨が経緯の記録に書かれていることをもって合格とする。
- **根拠として出すもの**: 該当箇所のファイル名と行番号。

### v5.0.0-8.2.1

- **原文**: Verify that the application ensures that function-level access is restricted to consumers with explicit permissions.
- **日本語**: 機能ごとのアクセスが、明示的に権限を与えられた利用者だけに制限されていること。
- **判定のしかた**: 機械
- **命令の種類**: 対象の一覧を作る命令
- **合格基準**: 次の命令を実行し、**前半の一覧のすべてが後半の一覧に含まれていること**。

  ```
  { echo "--- 外から触れるテーブル ---"; grep -hoiE 'create table +(if not exists +)?"?public"?\."?[a-z_0-9]+"?' supabase/migrations/*.sql | sed -E 's/.*[.]"?([a-z_0-9]+)"?$/public.\1/' | sort -u; echo "--- 行単位のアクセス制御が有効なもの ---"; grep -hoiE 'alter table +"?public"?\."?[a-z_0-9]+"? +enable row level security' supabase/migrations/*.sql | sed -E 's/^alter table +//I; s/ +enable.*$//I; s/"//g' | sort -u; }
  ```

  - 前半にあって後半に無いテーブルが1つでもあれば**不合格**。
  - **前半の一覧が0件なら判定不能**。テーブルを作る書きかたが命令と合っていないか、置き場所が違う。合格に倒さない。
- **該当しない条件**: ブラウザからデータベースへ直接つなぐ作りでない場合。そのときは、機能ごとの権限確認がサーバ側のどこで行われているかを読んで判定し、判定のしかたを `読む` として記録する。
- **根拠として出すもの**: 命令の出力そのもの。前半・後半それぞれの件数も記録する。
- **この判定が見ていないもの**: 命令が読むのは**移行ファイルに書かれた設計**であり、**いま動いているデータベースの実状ではない**。実状は Supabase 公式の点検機能（`0013_rls_disabled_in_public`）が見る。両方が必要。

### v5.0.0-8.2.2

- **原文**: Verify that the application ensures that data-specific access is restricted to consumers with explicit permissions to specific data items to mitigate insecure direct object reference (IDOR) and broken object level authorization (BOLA).
- **日本語**: データごとのアクセスが、その個々のデータに対して明示的に権限を与えられた利用者だけに制限されていること（他人の ID を指定すれば他人のデータが読める、という事故を防ぐため）。
- **判定のしかた**: 機械
- **命令の種類**: 対象の一覧を作る命令
- **合格基準**: 次の命令を実行し、**2行目が `0` であること**。改行をまたいで書かれた規則も見つけられるよう、いったん1行につないでから数える。

  ```
  { ls -1 supabase/migrations/*.sql | wc -l; cat supabase/migrations/*.sql | tr '\n' ' ' | grep -coiE 'using *\( *true *\)|with check *\( *true *\)'; }
  ```

  - 1行目は読んだファイルの数。**1行目が `0` なら判定不能**（置き場所が違う。合格に倒さない）。
  - 2行目は、誰でも通る全面許可の規則の数。**1以上なら不合格**。
  - 行単位のアクセス制御が有効で規則が1つも無いテーブルは、全面拒否になるため**合格**として扱う。規則が無いこと自体は危険ではない。危険なのは、規則が有っても中身が「全員可」であることのほうである。
- **該当しない条件**: 8.2.1 と同じ。ブラウザからデータベースへ直接つなぐ作りでない場合は `読む` で判定する。
- **根拠として出すもの**: 命令の出力の2行そのもの。

### v5.0.0-8.3.1

- **原文**: Verify that the application enforces authorization rules at a trusted service layer and doesn't rely on controls that an untrusted consumer could manipulate, such as client-side JavaScript.
- **日本語**: 認可の規則が、信頼できるサーバ側の層で強制されていること。ブラウザ側の JavaScript のように、利用者が書き換えられるものに頼っていないこと。
- **判定のしかた**: 読む
- **見る場所**: 次の3つの命令の出力に挙がった箇所だけを読む。ここに挙がらない場所は見ない。

  ```
  grep -rn 'revoke all on function' supabase/migrations/ | head -40
  grep -rnoiE 'service_role|sb_secret|SERVICE_ROLE_KEY' --include='*.js' --include='*.mjs' --include='*.html' . | grep -v node_modules
  grep -rn 'KEY\|TOKEN' .env.example
  ```

- **合格基準**: 次の3つをすべて満たすこと。1つでも欠ければ不合格。
  1. 認可の判定が、データベースの規則またはサーバ側で動く関数で行われており、その関数がブラウザから直接呼べないよう権限を剥奪されていること（1つ目の命令の出力で確かめる）
  2. ブラウザに渡している鍵が、その認可を迂回できる種類（Supabase の `service_role` 鍵に相当する、すべての制限を無視できる鍵）でないこと。2つ目の命令の出力に鍵の値が現れないこと。注釈の中に語が出るだけなら、その行を読んで注釈であると確かめたうえで合格としてよい
  3. ブラウザとデータベースの間にサーバ側の中継がある場合、その中継も迂回できる鍵を使っていないこと。中継が無い作りであれば 1 と 2 だけで判定する
- **該当しない条件**: 無い。
- **根拠として出すもの**: 3つそれぞれについて、確かめたファイル名と行番号。鍵については、迂回できる鍵が使われていないことを示した検索結果そのもの。
