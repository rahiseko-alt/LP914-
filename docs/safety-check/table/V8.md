# 固定表 — V8 認可（Authorization）

OWASP ASVS 5.0.0 の L1 のうち、章 V8 に属する **4項目**。項目は公式データ
（`../asvs-5.0.0-l1.csv`）と1対1で対応し、追加・削除・統合をしない。

判定のしかたは `機械`（実行する命令が確定しているもの）か `読む`（見る場所が確定している
もの）のどちらか。`機械` の命令は**対象アプリの置き場所の最上位で実行する**。

出典: OWASP Application Security Verification Standard 5.0.0 (CC BY-SA 4.0)。
日本語は原文からの訳で、訳の責任はこの置き場所にある（`docs/adr/0004` 参照）。

---

### v5.0.0-8.1.1

- **原文**: Verify that authorization documentation defines rules for restricting function-level and data-specific access based on consumer permissions and resource attributes.
- **日本語**: 認可の文書に、利用者の権限と対象の属性にもとづいて、機能ごとのアクセスとデータごとのアクセスを制限する規則が定められていること。
- **判定のしかた**: 読む
- **合格条件**: 経緯の記録の中に、**役割の一覧**と、**役割ごとに読める対象・書ける対象**を一覧できる箇所が1つ以上あること。役割が列挙されているだけ、または個別の決定の記録に断片的に散っているだけでは不合格とする。
- **該当しない条件**: 該当しない構成は無い。認可を持たないアプリ（全員が同じものを見る）であれば、その旨が経緯の記録に書かれていることをもって合格とする。
- **根拠として出すもの**: 該当箇所のファイル名と行番号。

### v5.0.0-8.2.1

- **原文**: Verify that the application ensures that function-level access is restricted to consumers with explicit permissions.
- **日本語**: 機能ごとのアクセスが、明示的に権限を与えられた利用者だけに制限されていること。
- **判定のしかた**: 機械
- **合格条件**: 次の命令の出力が**空**であること（＝外部から触れるテーブルで、行単位のアクセス制御が有効になっていないものが0件）。1行でも出れば不合格。

  ```
  comm -23 <(grep -hoiE 'create table public\.[a-z_]+' supabase/migrations/*.sql | sed 's/.*public\./public./' | sort -u) <(grep -hoiE 'alter table public\.[a-z_]+ enable row level security' supabase/migrations/*.sql | sed -E 's/^alter table //I; s/ enable.*$//I' | sort -u)
  ```

  この命令が見るのは**宣言されたスキーマ**であり、稼働中のデータベースの実状ではない。稼働中の実状は Supabase 公式診断の `0013_rls_disabled_in_public` が見る。両方が必要。
- **該当しない条件**: Supabase（PostgREST 経由でブラウザからデータベースに直接触る構成）を使っていない場合。その場合は、機能ごとの権限確認がサーバ側のどこで行われているかを `読む` で判定する。
- **根拠として出すもの**: 命令の出力そのもの。空であれば「出力0行」と記録する。

### v5.0.0-8.2.2

- **原文**: Verify that the application ensures that data-specific access is restricted to consumers with explicit permissions to specific data items to mitigate insecure direct object reference (IDOR) and broken object level authorization (BOLA).
- **日本語**: データごとのアクセスが、その個々のデータに対して明示的に権限を与えられた利用者だけに制限されていること（他人の ID を指定すれば他人のデータが読める、という事故を防ぐため）。
- **判定のしかた**: 機械
- **合格条件**: 次の命令の出力が**空**であること（＝誰でも通る全面許可の規則が0件）。1行でも出れば不合格。

  ```
  grep -niE 'using *\( *true *\)|with check *\( *true *\)' supabase/migrations/*.sql
  ```

  行単位のアクセス制御が有効で規則が1つも無いテーブルは、全面拒否になるため**合格**として扱う。規則が無いこと自体は危険ではない。危険なのは、規則が有っても中身が「全員可」であることのほうである。
- **該当しない条件**: Supabase を使っていない場合。その場合は、データごとの権限確認がサーバ側のどこで行われているかを `読む` で判定する。
- **根拠として出すもの**: 命令の出力そのもの。空であれば「出力0行」と記録する。

### v5.0.0-8.3.1

- **原文**: Verify that the application enforces authorization rules at a trusted service layer and doesn't rely on controls that an untrusted consumer could manipulate, such as client-side JavaScript.
- **日本語**: 認可の規則が、信頼できるサーバ側の層で強制されていること。ブラウザ側の JavaScript のように、利用者が書き換えられるものに頼っていないこと。
- **判定のしかた**: 読む
- **合格条件**: 次の3つをすべて満たすこと。1つでも欠ければ不合格。
  1. 認可の判定が、データベースの規則またはサーバ側で動く関数で行われていること
  2. ブラウザに渡している鍵が、その認可を迂回できる種類（Supabase の `service_role` 鍵に相当するもの）でないこと
  3. ブラウザとデータベースの間にサーバ側の中継（Worker、API サーバ等）がある場合、その中継が認可を迂回できる鍵を使っていないこと。中継が無い構成であれば 1 と 2 のみで判定する
- **該当しない条件**: 該当しない構成は無い。
- **根拠として出すもの**: 3つそれぞれについて、確かめたファイル名と行番号。鍵については、迂回できる鍵が使われていないことを示した検索結果。
