# 固定表 — V2 検証と業務ロジック（Validation and Business Logic）

OWASP ASVS 5.0.0 の L1 のうち、章 V2 に属する **4項目**。項目は公式データ
（`../asvs-5.0.0-l1.csv`）と1対1で対応し、追加・削除・統合をしない。

判定のしかたは `機械`（実行する命令が確定しているもの）か `読む`（見る場所が確定している
もの）のどちらか。どちらの命令も、**対象アプリの置き場所の最上位で `bash` で実行する**。

出典: OWASP Application Security Verification Standard 5.0.0 (CC BY-SA 4.0)。
日本語は原文からの訳で、訳の責任はこの置き場所にある（`../../adr/0004` 参照）。

## この章の共通の但し書き

- **命令が何も見つけられなかったときは、合格ではなく判定不能とする**（`../../adr/0002`）。
- **命令の出力に紛らわしい行が出たときは、その行を読む。** 試験専用の道具だと確かめられた
  場合に限り数に入れない。**読まずに除外しない。**確かめた根拠を判定結果に残す。

【入力の検証を調べる命令】

```
grep -rlnE 'zod|joi|yup|ajv|valibot|schema|validate' worker/src/ backend/js/ src/ 2>/dev/null | head -20
```

### v5.0.0-2.1.1

- **原文**: Verify that the application's documentation defines input validation rules for how to check the validity of data items against an expected structure. This could be common data formats such as credit card numbers, email addresses, telephone numbers, or it could be an internal data format.
- **日本語**: 受け取る値をどう確かめるかの決まりが、文書に定められていること。
- **判定のしかた**: 読む
- **見る場所**: 次の命令で挙がった文書。0件なら経緯の記録の全ファイル。

  ```
  grep -rlniE '入力|検証|バリデーション|スキーマ|schema|validation|受け取る値' docs/ *.md 2>/dev/null
  ```

- **合格基準**: 挙がった文書のどれかに、**どの入力について、どんな形と範囲を許すか**が読み取れること。検証の仕組みがコードに存在するだけでは不合格ではなく**判定不能**とする（記録が欠けている）。ただし、**検証の決まりが1か所のコードにまとまっており、その場所が記録から辿れる**場合は、その場所を文書とみなして合格としてよい。
- **該当しない条件**: 無い。
- **根拠として出すもの**: 該当箇所のファイル名と行番号。

### v5.0.0-2.2.1

- **原文**: Verify that input is validated to enforce business or functional expectations for that input. This should either use positive validation against an allow list of values, patterns, and ranges, or be based on comparing the input to an expected structure and logical limits according to predefined rules. For L1, this can focus on input which is used to make specific business or security decisions.
- **日本語**: 受け取った値が、その場面で期待される形と範囲に収まっているかを確かめること。許す形を先に決めて、それ以外を弾く形が望ましい。
- **判定のしかた**: 読む
- **見る場所**: 【入力の検証を調べる命令】で挙がったファイル。
- **合格基準**: 判断や記録に使う入力について、**許す形・許す範囲が明示的に書かれていて、それ以外が弾かれる**こと。次の3つをすべて満たすこと。
  1. 想定していない項目が混ざっていたら弾く（余分な項目を黙って受け入れない）
  2. 文字数や数値の上限・下限が指定されている
  3. 決まった形を持つ値（識別子など）は、その形に合っているかを確かめている
- **該当しない条件**: 無い。
- **根拠として出すもの**: 3点それぞれについて、ファイル名と行番号。

### v5.0.0-2.2.2

- **原文**: Verify that the application is designed to enforce input validation at a trusted service layer. While client-side validation improves usability and should be encouraged, it must not be relied upon as a security control.
- **日本語**: 入力の確認を、信頼できるサーバ側で行うこと。ブラウザ側の確認は使い勝手のためのもので、守りとして頼ってはならない。
- **判定のしかた**: 読む
- **見る場所**: 【入力の検証を調べる命令】で挙がったファイル。そのうち**サーバ側で動くもの**と**ブラウザ側で動くもの**を分ける。
- **合格基準**: 2.2.1 で確かめた検証が、**サーバ側で動く場所に存在する**こと。ブラウザ側にしか無ければ不合格。サーバ側とブラウザ側の両方にあるのは問題ない。
- **該当しない条件**: 無い。
- **根拠として出すもの**: サーバ側の検証のファイル名と行番号。そのファイルがサーバ側で動くことを示す根拠も。

### v5.0.0-2.3.1

- **原文**: Verify that the application will only process business logic flows for the same user in the expected sequential step order and without skipping steps.
- **日本語**: 決まった順序で進む手続きについて、順序どおりでない要求や、途中を飛ばした要求を受け付けないこと。
- **判定のしかた**: 読む
- **見る場所**: 次の命令の出力に挙がった箇所。

  ```
  grep -rnoiE "status *= *'|status *in *\(|state *= *'|draft|final|deleting|完了|確定" supabase/migrations/*.sql | head -30
  ```

- **合格基準**: 順序のある手続きについて、**次の段へ進む条件がサーバ側で確かめられている**こと。いまの段が期待どおりでなければ弾かれること。ブラウザ側の画面遷移だけで順序を守らせている場合は不合格。
- **該当しない条件**: 順序のある手続きが存在しない場合。
- **根拠として出すもの**: 段の条件を確かめている箇所のファイル名と行番号。
